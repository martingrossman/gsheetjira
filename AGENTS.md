# AGENTS.md — GSheetJira Codex Working Agreement

You are coding on **GSheetJira/SheetFlow**, a Google Sheets-backed project/task manager with a local standalone demo. The goal of this workstream is **exceptional usability, design consistency and speed**, not feature expansion for its own sake.

## Required reading before modifying code

1. `docs/PRODUCT_REQUIREMENTS_MVP.md` — approved MVP product scope and acceptance.
2. `docs/UI_UX_DESIGN_SPEC.md` — authoritative interaction and visual contract.
3. `docs/IMPLEMENTATION_PLAN_MVP.md` — implementation phases and quality gates.
4. `docs/FUTURE_ROADMAP.md` — features explicitly excluded from MVP.
5. `docs/LEGACY_SCOPE_MAPPING.md` — original section-by-section disposition.
6. Existing `readme.md`, `ProductRequiremtns.md`, and `IMPLEMENTATION_PLAN.md` for existing behavior and long-term context. Do **not** pull deferred features into the MVP from these older documents.

In case of conflict: **data safety > MVP functional requirements > UX details > implementation suggestions**. Surface unresolved design/functional conflicts in your report. Do not expand scope silently.

## Non-negotiable boundaries

- **Do not implement agentic task workflows in this MVP.** Codex is the *developer*, not a task runner integrated into the product. No claim APIs, autonomous agents, stale claims or orchestration UI.
- Preserve **both** working modes: standalone static/local browser (`localStorage`) and Apps Script web app (Google Sheets). They must never misleadingly claim to synchronize with each other.
- Preserve existing user data, IDs, parent/dependency validation, ordering semantics, conflict safety, CSV export and existing Gantt functionality. Avoid schema migrations unless specifically authorized with backup, test and rollback.
- Prefer incremental changes to current dependency-free HTML/CSS/JS and shared `Core.js`. **Do not introduce React, Next.js, a database, bundler, UI component framework or state-management library without an explicit trade-off review and approval.**
- Never modify production spreadsheets, run `setupTracker` on production, publish a deployment, execute `clasp push`, force-push, or merge/push branches without explicit approval. Verify the target Apps Script project, spreadsheet and environment for any approved deploy.
- Do not commit credentials, tokens, private Sheet IDs, `.clasp` secrets or user data to docs, test fixtures or source control.
- No hand-edits to build-owned output where regeneration is required. `CoreScript.html` and `dist/index.html` are generated by `npm run build`; update source and rebuild. Review tracked generated diffs.

## Local environment and commands

```sh
npm run build   # creates CoreScript.html and dist/index.html
npm test        # Node test runner
npm run check  # build and tests
npm start      # serves at http://127.0.0.1:4173
```

Node 18+ is documented. On Windows PowerShell, `npm.cmd` may be necessary. `clasp` is only for a specifically approved and verified Apps Script deployment. Current direct view hashes: `#sheet`, `#kanban`, `#gantt`.

Relevant files: `Index.html` (shell/forms), `Styles.html` (styling), `Client.html` (client interactions), `Core.js` (shared model/validation), `Code.js` (server/Sheets logic), `scripts/build.mjs` (standalone build), `tests/` (existing tests). Inspect actual code before proposing changes; these descriptions are a starting point, not exhaustive.

## Required coding loop

For every small work item:

1. **Inspect** source and existing tests; state actual behavior, risks, and affected files.
2. **Plan** a reviewable change with explicit acceptance criteria and scope exclusions.
3. **Implement** only the agreed slice. Prefer direct, coherent code over speculative abstractions.
4. **Verify** with `npm run check`, relevant interaction tests and real-browser checks where available. Test both modes when the change touches persistence or build/runtime differences. If the environment cannot run a test, report that plainly; do not claim it passed.
5. **Report** changes, screenshots/measurements when useful, regressions checked, current limitations and next slice. Do not mark an item done on visual plausibility alone.

Do not bundle visual redesign, data migration, backend write-path refactor and new features into one unreviewable change.

## UX quality rules

- Minimal visual appearance + balanced discoverability; keyboard and mouse must both be efficient.
- **Title-only fast creation**; common properties directly editable; advanced fields in details panel.
- Preserve useful focus, selection, filter and scroll state across routine changes.
- Use design tokens and accessible semantic colors; no pervasive tiny text, inconsistent random colors or duplicate navigation.
- Dialogs must trap/restore focus, support Escape appropriately and preserve unsaved drafts.
- Avoid hover-only functionality; provide keyboard/touch alternatives, feedback and accessible labels.
- Maintain existing shortcuts `N`, `/`, `1`, `2`, `3`, `Esc`; handle typing fields, IME composition and modifier keys correctly. Add others only without conflict.

## Speed and persistence rules

- Treat smooth animations as **not a substitute for speed**. Measure under defined conditions, including a 2,000-task dataset.
- Targets: local feedback p95 <100 ms; loaded-view navigation p95 <150 ms; initial usable view target <3s; typical Apps Script save target <2s under documented conditions. These are goals requiring evidence, not current guarantees.
- Display accurate **Pending/Saving, Saved, Failed, Conflict** states. A local optimistic update is not a successful server save.
- A rejected or timed-out inline edit must retain the user's draft for retry/copy/conflict resolution. Do not silently overwrite newer remote data.
- Use safe mutation ordering, targeted rendering and debouncing where justified. Retain correct behavior on failed requests, long latency and quick successive edits.

## Phase/release gates

- Phase 0: baseline report, risk map, branch and test plan; **no code changes** until approved.
- Subsequent phases: small PR/commit series with acceptance checks from the plan.
- Stop and request approval before adding new dependencies, altering the Sheets schema, expanding product scope, changing authentication/sharing or deploying to production.
